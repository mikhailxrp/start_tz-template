# Регламент: написание ТЗ из брифа

Процесс рассчитан на работу в среде с файлами (Claude Code, Cowork). В чате выполнимы только сессии S1–S3.

---

## Структура папки

```
project-name/
├── 00-input/                 ← только чтение, агент не пишет сюда
│   ├── brief.md
│   └── attachments/
├── 01-tz/
│   ├── tz.md                 ← растёт по разделам
│   ├── decisions.md          ← журнал решений
│   └── coverage.md           ← карта заполнения
├── 02-sdd/
└── tools/
    └── check_tz.py
```

Подготовка:

```bash
git init && git add . && git commit -m "input: brief + attachments"
cp template-tz.md 01-tz/tz.md
```

## Команда старта сессии

Единая формулировка. Меняются только номера.

```
Прочитай:
- 01-tz/decisions.md
- разделы 4-6 файла 01-tz/tz.md
- 00-input/brief.md, пункты [номера]

Заполни раздел [N] в 01-tz/tz.md.
Формат требований — п. 4.3 системного промпта, без сокращений.

После записи выведи:
- количество требований и их ID
- какие пункты брифа остались непокрытыми
- что пришлось решить самому (маркер /Р) и почему
```

Последний блок обязателен. Он превращает молчаливое сокращение в видимое.

## Журнал решений

`01-tz/decisions.md` — читается агентом в начале каждой сессии.

```markdown
| Дата | Решение | Почему | Отвергли | Раздел |
|---|---|---|---|---|
| 12.03 | Варианты товара на одной странице | SEO по брендам не приоритет (бриф 7.1) | Отдельные URL — дороже, выгода не доказана | 6.2 |
```

Без этого файла каждая сессия начинает с нуля и может перерешать закрытый вопрос.

## Валидация

```bash
python3 tools/check_tz.py 01-tz/tz.md
python3 tools/check_tz.py 01-tz/tz.md --strict   # для CI / pre-commit
```

Что ловит:

| Проверка | Уровень |
|---|---|
| Дубли идентификаторов | ERROR |
| Требование без маркера `/Б` или `/Р` | ERROR |
| Требование без критериев приёмки | ERROR |
| Модуль вне справочника, `PRD` вместо `CARD` | ERROR |
| Приоритет вне MoSCoW | ERROR |
| Отсутствие критичных разделов 3.1, 4, 5.2, 6.3, 10.1, 11.6, 14 | ERROR |
| Отсутствие полей «Очередь», «Роль», «Источник» | WARN |
| Расплывчатые формулировки | WARN |
| Тело требования короче 5 строк — признак дрейфа формата | WARN |
| Ссылка на несуществующий ID | WARN |
| Остатки шаблона (`← бриф п.`, `[УДАЛИТЬ ЕСЛИ`) | WARN |

Чего НЕ ловит: противоречия по смыслу, пропущенные сценарии, неверные бизнес-правила. Для этого — сессия S11.

Опционально в pre-commit hook:

```bash
echo 'python3 tools/check_tz.py 01-tz/tz.md --strict' > .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

## Промпт ревьюера (сессия S11)

Запускается **новой сессией**, не той, что писала документ.

```
Ты — независимый ревьюер технических заданий. Ты НЕ писал этот документ.

Прочитай 01-tz/tz.md целиком. Твоя задача — найти дефекты, а не похвалить.

Ищи в таком порядке:
1. Противоречия между требованиями разных разделов
2. Термины, использованные не по глоссарию (раздел 4)
3. Сценарии из раздела 7, не покрытые требованиями раздела 8
4. Статусы из раздела 6.3, для которых нет требований о переходах
5. Роли из раздела 5, не фигурирующие ни в одном сценарии
6. Требования, где критерий приёмки не проверяет само требование
7. Места, где формат требований деградировал к концу документа

Выдай таблицу: раздел | дефект | последствие | как исправить.
Не предлагай улучшений стиля. Только дефекты.
Если дефектов не нашёл — скажи прямо, не выдумывай.
```

## Признаки, что процесс поехал

Проверять глазами раз в несколько сессий:

| Симптом | Что произошло | Действие |
|---|---|---|
| Средняя длина требования падает от раздела к разделу | Дрейф формата | Вернуть агента к п. 4.3, переписать последний раздел |
| Растёт доля маркеров `/Р` | Агент додумывает вместо вопросов | Проверить, задавались ли вопросы клиенту |
| Появились термины не из глоссария | Контекст потерян | Явно вставлять раздел 4 в начало каждой сессии |
| Модуль закрыт 3 требованиями | Молчаливое сокращение | Сверить с картой `coverage.md` |
| Раздел написан без единой ссылки на бриф | Агент писал по памяти | Переписать с явным указанием пунктов |

## Что остаётся риском

Этот регламент снижает риск потерь, но не убирает его. Не покрывается ничем автоматическим:

- Требование написано корректно по форме, но неверно по сути
- Пропущен сценарий, о котором никто не подумал
- Бизнес-правило противоречит реальному процессу клиента

Единственная защита — согласование ТЗ с клиентом по разделам 1, 6.3, 9 и 14. Именно эти четыре раздела он способен проверить по существу.
