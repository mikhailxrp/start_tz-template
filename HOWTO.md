# Как пользоваться шаблоном ТЗ

## Что это такое

Представьте цех по производству документов. На входе — анкета, которую заполнил владелец магазина. На выходе — техническое задание, по которому можно писать код.

```
Бриф  →  ТЗ  →  SDD  →  Код
      ↑
   этот цех
```

**Бриф** — анкета для клиента. Вопросы про его бизнес, без единого технического слова.

**ТЗ** — перевод «хотелок клиента» на язык, понятный программисту. Пишет Claude, вы контролируете.

**SDD** — план стройки. Следующий этап, пока не собран.

---

## Что лежит в папках

```
D:\Development\tz-template\      ← ЭТАЛОН, отсюда копируется
```

| Что | Зачем |
|---|---|
| `CLAUDE.md` | 13 правил для Claude. Он читает их каждый раз |
| `HOWTO.md` | Этот файл |
| `reference\` | Образцы: анкета, форма ТЗ, инструкции для агентов |
| `tools\check_tz.py` | Проверяльщик готового ТЗ |
| `tools\new-project.ps1` | Создаёт папку под нового клиента |
| `.claude\commands\` | 11 команд, которые понимает Claude |
| `template\` | Пустая заготовка проекта |
| `_test\` | Тестовый магазин для проверки шаблона после правок |

**Главное правило:** в `tz-template` вы не работаете. Это склад образцов. Работа идёт в папках клиентов.

---

## Начало работы с клиентом

### Шаг 1. Отправить анкету

Файл: `D:\Development\tz-template\reference\brief-ecommerce.md`

Отправьте клиенту. Он не программист — вопросы написаны понятным языком.

Отдельно попросите:
- выгрузку 20–30 товаров в Excel (заменяет десяток уточнений)
- макеты дизайна, если есть
- ссылку на текущий сайт

### Шаг 2. Создать папку проекта

```powershell
cd D:\Development\tz-template
.\tools\new-project.ps1 -Name "имя-клиента"
```

Появится `D:\Development\имя-клиента` со всем необходимым.

Имя латиницей, без пробелов: `acme-shop`, `lapa-shop`.

### Шаг 3. Разложить файлы клиента

```
D:\Development\имя-клиента\00-input\
    brief.md          ← заполненная анкета, именно с таким именем
    attachments\      ← Excel, прайсы, скриншоты
    design\           ← макеты экранов
```

Макеты называйте по смыслу: `01-glavnaya.png`, `02-katalog.png`. По имени Claude поймёт, какой это экран.

### Шаг 4. Открыть Claude Code

```powershell
cd D:\Development\имя-клиента
claude
```

Дальше — команды.

## Команды

### 1. `/tz-start` — разбор анкеты

Claude читает бриф и говорит, чего не хватает: пробелы, противоречия, риски.

**Получите:** реестры вопросов, противоречий, допущений. Плюс карту заполнения.

**Не пропускайте.** Здесь ловятся дыры, которые потом стоят недель.

### 2. `/tz-questions` — письмо клиенту

Превращает технический реестр в человеческое письмо: что непонятно, почему спрашиваем, варианты ответа.

**Получите:** файл `01-tz\questions-for-client.md`.

**Что делать:** отправить клиенту, дождаться ответов.

### 3. `/tz-answers` — разбор ответов

Ответы клиента положите в `00-input\answers.md` и запустите команду.

Claude сопоставит их с вопросами, закроет что можно, обновит журнал решений.

**Важно:** ответ «не знаю, предложите сами» вопрос **не закрывает**. Он становится допущением, и требование получает пометку «решил аналитик», а не «сказал клиент».

### 4. `/tz-model` — язык документа

Разделы 4–6: что такое товар, чем он отличается от варианта, какие роли, какие статусы у заказа.

**Самый важный этап.** Ошибка здесь размножится по всем требованиям.

**Что проверить:** откройте `01-tz\tz.md`, прочитайте раздел 4. Термины должны быть понятны вам. Если что-то звучит странно — скажите Claude.

### 5. `/tz-scenarios` — сценарии

Что происходит, когда покупатель что-то делает. Включая неприятное: товар кончился во время оплаты, деньги списались дважды, 1С отвалилась.

**Что проверить:** в отчёте должно быть разобрано 9–11 ошибочных веток из 11. Если больше двух отмечено «неприменимо» — Claude экономит, спросите почему.

### 6. `/tz-screens` — реестр экранов

**Только если есть макеты.** Claude составит список экранов с номерами `SCR-01`, `SCR-02` и найдёт недостающие состояния.

**Что такое недостающие состояния.** Дизайнер рисует «как всё хорошо»: товары есть, данные загрузились. А в жизни бывает пустой каталог, ошибка оплаты, экран загрузки. Этих экранов обычно нет — Claude их перечислит, дорисует дизайнер.

**Зачем это нужно.** Если макеты есть, требования становятся короче втрое: не описываем словами то, что видно на картинке, описываем только поведение.

### 7–10. `/tz-modules` — сами требования

Основной объём. Запускайте **четырьмя отдельными командами**, по одной за раз:

```
/tz-modules 8.0 8.1 8.2 8.3 8.18
/tz-modules 8.4 8.5 8.6 8.7
/tz-modules 8.8 8.9 8.10 8.11
/tz-modules 8.12 8.13 8.14 8.15 8.16 8.17
```

**Почему не всё сразу.** Попросив всё разом, получите деградацию: к концу требования станут короче и хуже. Порциями качество ровное — проверено на тестовом прогоне.

**После каждой команды:**

```powershell
git add . ; git commit -m "tz: modules 8.4-8.7"
```

### 11. `/tz-ai` — ИИ-помощники

**Только если клиент выбрал их в брифе (часть 14).**

Требования к автоматизации: разбор характеристик, генератор описаний, консультант в чате.

**Особые правила.** Каждое ИИ-требование обязано указывать: какой провайдер (российский или любой), кто проверяет результат до публикации, что происходит при недоступности сервиса. Без этих трёх строк проверяльщик даст ошибку.

Причина строгости: промпт с телефоном покупателя, ушедший в зарубежный сервис, — это нарушение 152-ФЗ, а не техническая мелочь.

### 12. `/tz-rules` — правила и интеграции

Разделы 9–14: бизнес-правила, интеграции, требования к скорости и надёжности, критерии приёмки.

**Что проверить:** раздел 10.1 «Источник истины». Там таблица: для каждого типа данных указано, кто главный — сайт или 1С. Если хоть одна строка пустая, при интеграции получите цикл обновлений или потерю данных.

### 13. `/tz-summary` — резюме

Разделы 1–3. Пишутся последними намеренно: теперь объём известен, и резюме не разойдётся с содержанием.

### 14. `/tz-review` — ревью

**Закройте Claude Code и откройте заново.**

```powershell
exit
claude
/tz-review
```

Свежая сессия прочитает документ как чужой и найдёт противоречия.

**Почему обязательно новая сессия.** Тот, кто писал, помнит свои обоснования и будет их защищать. Автор своих дыр не видит — ни человек, ни Claude.

**Норма:** 3–10 найденных дефектов. Ноль — подозрительно. Больше двадцати — либо придирки к стилю, либо в документе беда.

## Проверка руками

В любой момент:

```powershell
python tools\check_tz.py 01-tz\tz.md
```

Что показывает:

| Строка | Значение |
|---|---|
| `Требований найдено: 95 (полный: 33, табличный: 62)` | Сколько и в каком формате |
| `из брифа: 89` | Столько сказал клиент |
| `решение аналитика: 6` | Столько придумал Claude |
| `Ошибок: 0` | Всё в порядке |

**Тревожный знак:** «решение аналитика» больше трети — Claude слишком много додумал вместо того, чтобы спросить клиента.

## Два формата требований

Не всё описывается одинаково подробно.

**Полный формат** — деньги, склад, права, оформление заказа. Двадцать строк: приоритет, правила, критерии приёмки, связи.

**Табличный** — интерфейс, навигация, отображение. Одна строка:

```
| FR-CAT-005/Б | Пагинация и «показать ещё» | MUST/MVP | все | Список >1 стр → номера и кнопка |
```

Claude выбирает формат сам по правилу: полный, если требование затрагивает деньги, остатки, права доступа, зависит от внешней системы или имеет больше двух ошибочных веток.

**Зачем это.** Одинаково подробно описывать пересчёт цен при оплате и наличие хлебных крошек — значит утопить важное в рутинном. Без разделения ТЗ выходит на 84 страницы, с ним — на 30.

## Если что-то пошло не так

| Проблема | Что сказать Claude |
|---|---|
| Требования становятся короче | «Нарушено правило 7 из CLAUDE.md, перепиши раздел» |
| Появились непонятные термины | «Используй только термины из раздела 4» |
| В модуле всего 3 требования | «Сверь с coverage.md, проверь покрытие пунктов брифа» |
| Пересказывает макет словами | «Оставь только поведение сверх макета, ссылайся на SCR-NN» |
| Придумал факт | «Это не из брифа. Заведи Q-NNN вместо догадки» |

Откатить последнюю сессию:

```powershell
git checkout -- 01-tz\tz.md
```

## Как улучшать шаблон

Заметили, что Claude чего-то не учитывает? Правьте **эталон**, не копию в проекте:

```powershell
cd D:\Development\tz-template
# правки в reference\ или .claude\commands\
git add . ; git commit -m "prompt: правило про X"
```

Следующий проект получит улучшение. Текущий — нет, и это правильно: менять правила посреди работы хуже, чем дожить со старыми.

**Проверка после правок.** В папке `_test\` лежат ключи к тестовому магазину «Лапа». Прогоните на нём `/tz-start` и сверьте с ключом — так вы поймёте, не сломали ли что-то.

---

## Три вещи, которые стоит запомнить

1. **`tz-template` — склад, а не рабочее место.** Работа всегда в папке клиента.

2. **Не пропускать `/tz-start`.** Соблазн будет: кажется, можно сразу писать требования. Нельзя — там ловятся дыры, которые потом стоят недель.

3. **`/tz-review` — новой сессией.** Автор своих ошибок не видит.
