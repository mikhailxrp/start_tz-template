## Определи режим источника

Три источника дают разное качество информации. Определи, с чем работаешь,
до того как начнёшь заполнять реестр.

| Признак во входных данных | Режим |
|---|---|
| `.png`, `.jpg`, `.jpeg` в `00-input/design/` | **Скриншоты** |
| Ссылка на Figma в брифе п. 11.1 | **Figma** |
| `.html` файлы (обычно с папкой `assets/`) в `00-input/design/` | **Вёрстка** |
| Смесь — например, часть страниц скриншотами, часть вёрсткой | Определяй режим **отдельно по каждому экрану** |

Режим влияет только на то, откуда ты берёшь факты. Итоговый реестр
и формат требований в разделе 8 не отличаются между режимами.

### Режим «Скриншоты»

Ты смотришь на изображение. Извлекаешь: состав блоков, видимый текст,
расположение. Не видишь: обязательность полей, состояние при ошибке
(если не нарисовано отдельным кадром), поведение при клике — это всё
никогда не следует из статичной картинки, только из брифа или логики.

### Режим «Figma»

Если подключён MCP-коннектор Figma — используй его для чтения структуры
экрана. Если не подключён — попроси человека выгрузить нужные экраны
как изображения и работай в режиме «Скриншоты».

### Режим «Вёрстка» (HTML/CSS)

Ты читаешь файлы как код, не как картинку. Это даёт больше фактов, чем
скриншот, но требует аккуратности: вёрстка показывает форму интерфейса,
а не его поведение. Кнопки ведут в никуда (`href="#"`), обработчиков нет —
это нормально, макет и не должен их содержать.

**Как читать один HTML-файл:**

1. **Имя файла — это состояние экрана, не обязательно новый экран.**
   `cart.html` и `empty-cart.html`, `checkout.html` и `checkout-empty.html` —
   типичная пара «есть данные / нет данных» для одного и того же экрана.
   Сопоставляй по смысловой части имени (`cart` = корзина) и заводи
   **один** `SCR-*` с перечислением файлов-состояний. Задвоить экран
   на пустом месте — частая ошибка, которую легко не заметить.

2. **Формы: ищи `<form>`, `<input>`, `<select>`, `<textarea>`, `<button>`.**
   Из атрибутов `name`/`id` бери техническое имя поля, если оно осмысленное
   (`email`, `phone`) — не бери, если это генерированное `field-23`.

3. **Обязательность поля определяй по совокупности признаков, не по одному:**
   - атрибут `required` — надёжный сигнал, но в готовых вёрстках
     встречается редко;
   - звёздочка в `placeholder` или в соседнем `<label>` (`"First name *"`) —
     частый способ показать обязательность визуально;
   - если нет ни того, ни другого — поле считается опциональным,
     не домысливай.

4. **Варианты выбора** (радиокнопки, чекбоксы, `<select>`) — перечисли
   все опции текстом из разметки: подписи `<label for="...">`, текст
   внутри `<option>`. Это фактические данные из макета, а не догадка —
   их обязательно перепроверить с клиентом на предмет полноты списка
   (макет мог отрисовать «для примера», а не финальный набор).

5. **Повторяющиеся блоки** (карточка товара в сетке каталога, строка
   таблицы) описывай один раз со словом «карточка/строка повторяется»,
   не как N отдельных объектов.

6. **Что НЕ следует из вёрстки** — не выдумывай на основе кода:
   - что происходит при клике (`href="#"`, `action="#"` — заглушки);
   - валидацию сложнее, чем видимая пометка обязательности;
   - данные, которые подставлены в поля (все значения в вёрстке —
     тестовые/примерные, не бери их как факт о реальном ассортименте).

7. **Классы и структура — ключ к состояниям, которых не хватает.**
   Если у экрана есть файл-пара «пусто/заполнено» — оба состояния уже
   покрыты, в недостающие не заноси. Если пары нет и по смыслу экрана
   пустое состояние нужно (каталог, поиск, история заказов) — это
   недостающее состояние, как и в режиме скриншотов.

## Что сделать

Создай `01-tz/screens.md` — реестр экранов. Он станет источником ссылок
`SCR-NN` для требований раздела 8.

### Структура реестра

```markdown
# Реестр экранов

Источник: `00-input/design/`
Режим: [скриншоты / Figma / вёрстка / смешанный]
Состояние дизайна: [финальный / может меняться / черновик] — из брифа п. 11.1

| ID | Экран | Источник | Разделы ТЗ | Роль | Состояния |
|---|---|---|---|---|---|
| SCR-01 | Главная | 01-glavnaya.png | 8.0 HOME | Гость, Покупатель | основное |
| SCR-02 | Каталог | shop-grid-left-sidebar.html | 8.1 CAT | все | основное, пустой результат (нет в макете) |
| SCR-03 | Корзина | cart.html, empty-cart.html | 8.4 CART | Покупатель | заполнена, пусто |
```

Колонка «Источник» — имя файла (или нескольких файлов-состояний) либо
узел Figma. Колонка «Разделы ТЗ» связывает экран с подразделами раздела 8 —
по ней требования будут ссылаться на макет.

**Для режима «Вёрстка» дополнительно** заведи блок с извлечёнными фактами
по каждому экрану, где есть формы или варианты выбора:

```markdown
### SCR-05 · Оформление заказа (checkout.html)

**Способы доставки** (радиокнопки, выбор один из трёх):
- Flat Rate
- Free Shipping
- Local Pickup

**Способы оплаты** (радиокнопки, по умолчанию выбрано «Наличные»):
- Банковский перевод
- Чек
- Наличные (умолчание в макете)
- PayPal

**Поля адреса доставки** (обязательные помечены `*` в подписи):
- Имя *
- Фамилия *
- Название компании (необязательно)
- Дом и улица *
- Квартира/офис (необязательно)
- Город *
- Индекс (без `*` в макете — уточнить обязательность у клиента)
- Телефон *
- Email *

⚠ Список способов оплаты/доставки — из демонстрационной вёрстки,
не факт брифа. Подтвердить с клиентом перед использованием в BR-001.
```

Это не пересказ ради пересказа: перечисленные варианты — кандидаты
в матрицу `BR-001` (оплата×доставка) и в поля формы `FR-CHK-*`, но
помеченные как требующие подтверждения, а не как готовый факт.

### Что проверить по каждому экрану

**Недостающие состояния.** Для каждого экрана проверь наличие:

| Состояние | Где обязательно |
|---|---|
| Пусто / нет результатов | каталог, поиск, корзина, избранное, история заказов |
| Ошибка | оформление, оплата, формы |
| Загрузка | всё, что тянет данные извне |
| Товар недоступен | карточка, корзина, оформление |
| Вид для роли без прав | админка, кабинет менеджера |
| Мобильная версия | все клиентские экраны |

В режиме «Вёрстка» сначала проверь, нет ли уже файла-пары для этого
состояния (см. п. 1 выше), и только потом заноси как недостающее.

Отсутствующее состояние — это не твоя выдумка текстом, а **работа дизайнера**.
Выноси списком, не описывай словами, как оно должно выглядеть.

**Расхождения с брифом.** Экран показывает блок, которого нет в брифе, или
бриф требует функцию, для которой нет экрана. И то и другое — `C-NNN`.
В режиме «Вёрстка» сюда же — данные, извлечённые из формы (варианты
доставки/оплаты, список полей), которые не совпадают с тем, что в брифе.

**Экраны без назначения.** Макет есть, а какому разделу ТЗ соответствует —
непонятно. Вопрос `Q-NNN`, не догадка.

## Отчёт

Выведи:

1. Режим источника (или режимы, если смешанный)
2. Сколько экранов в реестре, как распределились по разделам 8.x
3. **Разделы 8.x без единого экрана** — по ним требования пишутся текстом,
   как обычно
4. **Недостающие состояния** — таблицей: экран, какого состояния нет,
   для какого требования оно понадобится
5. Расхождения макетов с брифом (`C-NNN`)
6. Экраны без назначения (`Q-NNN`)
7. Для режима «Вёрстка»: факты, извлечённые из форм (варианты оплаты,
   доставки, обязательные поля), с пометкой «требует подтверждения клиентом»

Допиши строку в `01-tz/session-log.md`.

## Чего не делать

- Не описывай, что нарисовано на экране. Реестр — это карта, а не пересказ.
- Не выдумывай, как должны выглядеть недостающие состояния. Твоё дело —
  назвать пробел, закрывает его дизайнер.
- Не пиши требования. Это следующая команда.
- В режиме «Вёрстка»: не путай значения в демо-контенте (тестовые товары,
  примерные цены) с фактами о реальном ассортименте клиента.
- В режиме «Вёрстка»: не приписывай поведение (`onclick`, переходы) тому,
  чего в коде нет — заглушка `href="#"` означает «дизайнер не решал этот
  вопрос», а не «перехода никогда не будет».
