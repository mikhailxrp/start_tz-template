## Правила, специфичные для этого модуля

**Полный формат для всех требований.** Табличный формат здесь не применяется:
ошибка ИИ-функции видна покупателю, цена высокая.

**Каждое требование указывает четыре вещи сверх стандартных полей:**

| Поле | Почему обязательно |
|---|---|
| Провайдер (класс задачи) | Определяет юрисдикцию и стоимость |
| Проверка результата | Кто ловит ошибку до покупателя |
| Поведение при недоступности | Провайдер будет недоступен |
| Ограничение стоимости | Иначе счёт непредсказуем |

**Порядок задач.** Если в брифе выбраны и структуризация данных, и функции,
работающие на этих данных (смысловой поиск, подбор, фильтры) — зафиксируй
зависимость явно: помощник на неструктурированных данных выдаёт мусор.
Структуризация идёт первой очередью, остальное — после подтверждения качества.

**Персональные данные.** Проверь по каждому требованию, попадают ли в промпт
имя, телефон, адрес, состав заказа. Если да и в брифе п. 14.6 нет явного
разрешения — это `Q-NNN`, а не допущение. Ошибка здесь юридическая,
а не техническая.

**Не проектируй реализацию.** «Векторный поиск по эмбеддингам с косинусной
близостью» — решение архитектора. Требование звучит: «покупатель находит
Товар по описанию задачи, а не по точному названию».

**Что запрещено помощнику.** Из брифа п. 14.5 перенеси список запретов
в требование дословно. Формулировка «помощник не даёт ветеринарных советов» —
это требование с критерием приёмки, а не пожелание.

**Не обещай качество.** Формулировки «отвечает корректно», «понимает запрос»
непроверяемы. Критерий приёмки формулируется через наблюдаемое поведение:
что показано пользователю, что записано в базу, что попало на ревью.
